# Jev 在追番中心的使用价值与接入方案

日期：2026-09-20。状态：2026-09-21 已完成本地影视基础搜索/年份筛选、Jev 公开元数据实验首次 live、动漫/影视共用候选预览，以及 Windows 版 Bandi 直连 TypeSafe；真实本地候选已完成一次显式点击验收，Owner 盲标、效果评分和 NAS 服务端部署仍未完成。

## 结论

**值得试一个“按心情选片”的只读辅助功能，暂时没有把 Jev 变成媒体中心基础依赖的必要。** Bandi 已有相当完整的追更、筛选、资料、下载与播放链。Jev 的增量主要是理解题材标签之外的偏好，例如“轻松、不需要太专注、人物关系温暖”，把现有候选排得更符合这次想看的内容。

建议先验证“选片是否更快、前三个结果是否更合心意”，再决定做产品入口。优先级为：**心情/场景筛选 → 相似作品与主题片单 → 有证据的资料歧义辅助**。开发中的小 diff 初筛可继续复用现有全局路由，它与产品内选片是两条独立用途。

NAS 先作为媒体存储，由现有 Windows 版完成检索、Jev 调用和播放；把 Bandi 部署到 NAS 是另一项产品工程，当前没有必要与 Jev 同时推进。

## 1. 本轮核对到的现状

### 已有产品能力

- 本仓库是现行桌面主仓库，`package.json` 当前为 0.1.12。产品目标是“今天看什么、看到第几集、下集什么时候更新”，而非开放式聊天助手。版本号只表示源码包声明，本轮未核对运行中的 exe 或远端最新 release。
- 首页已有今日更新、继续观看、漏看提醒与未来预告；季度番库已有年份、季度、类型、题材、地区等筛选。影视与动漫各有本地库，扫描采用预览后确认。
- 共享 `anime` 表有标题、日文标题、简介、标签、类型、年份、播出状态、总集数、平台、外部标识与部分评分。`userAnime` 和播放记录承载个人进度等信息。
- `anime` 表没有完整目录级片长字段；`playbackProgress.durationSeconds` 是播放记录字段，默认可为 0，不能当成所有未播放影片的可靠片长。
- 资料来自多个公开来源及本地导入，字段存在并不表示每一条都完整。README 明确长门番堂主要提供档期和制作情报，不能把其资讯摘要当剧情简介。
- 顶部搜索的 `searchAnime()` 当前在本地按 `title/titleJa LIKE` 查询，最多 8 条、少于 5 条时调用 Bangumi fallback；返回的 `SearchHit` 不含简介和标签。语义选片不能只在这个返回值上套模型，需要单独准备只读候选 DTO，从已存元数据取简介与标签。影视查询已有本地库与资料库分流，能够复用范围筛选。
- 页面能力有差别：`/cinema-library` 已有追踪状态、类型、年份、精确标签、标题/原名与评分排序；`/cinema` 本地库目前主要是电影/电视剧和固定分类，没有同等的自由文本搜索、年份筛选。**若痛点是本地片库基础检索不够，先补这两项比调用 Jev 更直接。**
- `CinemaItem` 列表 DTO 也未暴露 synopsis；`buildCinemaItems` 还会排除成人、未刮削、豆瓣动画条目并去重。语义适配要保留这些确定性分区规则，同时明确未刮削条目不在当前候选中，不能用“无匹配”掩盖资料未准备好的情况。
- 当前搜索推荐接口使用继续观看、今日更新和本季日本高分 Top 4 等规则；这已经解决一部分“今天看什么”，本轮核对的入口未发现心情语义推荐。
- Windows 目录支持 UNC 共享。macOS Local Web 文档明确把 Linux、Docker/NAS 服务端排除在当前发布范围之外。访问 NAS 上的文件与在 NAS 上部署应用是不同能力。

### 调查边界

本轮读产品文档、schema、相关源码与测试定义，没有读取实际片单、播放历史、媒体文件、用户数据库或凭据，没有启动/打包应用，也没有探测 NAS。因而**不能报告你的真实片库规模、简介完整率、NAS 吞吐或实际推荐收益**。

仓库有多处正在修改的页面、动效和测试文件。本轮只新增本报告，不覆盖现有改动，不修改日常运行副本 `release/win-unpacked`。

## 2. 哪些场景值得融入

以下为基于现有能力的产品建议，不是已实现功能。

| 场景与用户说法 | 本地程序负责 | Jev 可补的部分 | 优先级与限制 |
|---|---|---|---|
| **按心情选片**：“今晚想看轻松温暖、不要一直打斗的” | 先限定动漫/电影、本地可播、未看等候选 | 根据简介与标签判断是否符合这次偏好 | **最适合首试**；不能从简介缺少暴力描写推出全片无暴力 |
| **场景组合筛选**：“吃饭时看，不想跟复杂主线” | 用户选择媒体类型，保留原筛选条件 | 判断简介体现的是日常单元内容还是复杂连续剧情 | 高；陌生作品与简介不全要允许资料不足 |
| **找相似作品**：“像这部，但更轻松、少一点恋爱” | 提供目标作品及宽一些的候选 | 分开比较氛围、主题、叙事结构，不只比较相同 genre | 中高；目标作品资料也必须足够，首轮不用完整观看史 |
| **主题片单**：“太空探索”“温暖群像”“悬疑但不猎奇” | 管理候选、去重、展示和人工保存 | 多标签语义判定，允许同一影片进入多个片单 | 中；每个标签独立判断，不能强迫单选标签 |
| **简短自然语言筛选**：“找近几年已完结、偏治愈的番” | 明确年份范围、完结状态等条件；展示可编辑筛选项 | 识别有限的偏好类别，补“治愈”这类语义匹配 | 中；“近几年”要显示实际年份，复杂语句保留未识别部分 |
| **资料匹配辅助**：同名、译名、电影与剧集候选难分 | 外部 ID、年份、季别、类型的硬匹配与否决 | 对剩下的少量候选比较简介与标题语义，提示最可能项 | 中低；先只读，不自动合并或覆盖身份 |
| **资料质量提醒**：标签与简介冲突、疑似抓错介绍 | 空字段、长度、重复与来源变更检查 | 标出语义冲突供复核 | 中低；Jev 不负责凭空补写剧情或纠正官方事实 |
| **字幕/资源候选理解**：命名混乱、说明含糊 | 分辨率、编码、字幕语言、季集号、文件存在等解析 | 少数无法靠解析区分的说明性文本 | 低；原找源规则已覆盖大量情况，不接自动下载 |
| **家庭观看提示** | 正式分级、显式成人分区与家长设置 | 基于已提供内容描述补充“可能含某类内容”的提示 | 低；不得把推测当分级或儿童安全保证 |
| **字幕内容搜索、场景检索** | 字幕提取、时间轴、候选检索 | 对已命中的字幕片段判断相关性 | 后续候选；新增索引、剧透和外发范围，不纳入首期 |

### 直接用普通代码更合适的部分

年份、评分、集数、更新时间、是否看过、是否已下载、剩余空间、文件哈希、分辨率、编码、字幕轨数量、播放进度与下一集选择，优先用程序和真实数据。不要让模型计算“还剩几集”，或猜“这个文件能不能播放”。

精确片名搜索优先原搜索；同一季别/外部 ID 的确定性识别优先原匹配。文件去重、删除、移动、下载与状态更新不由 Jev 自行执行。Jev 也不能解决编解码兼容、转码、NAS 性能与资料源缺失。

## 3. 必要性：何时值得，何时不用

**支持接入：**你如果经常知道想要的氛围却不知道片名，现有年份/题材筛选会留下大量需要逐个读简介的作品；语义筛选有机会减少这一步。片库中有足够可信的简介时，技术上可以做成小范围、随时关闭的辅助功能。

**最强反对意见：**Bandi 已有继续观看和今日更新，大多数日常追番可能只需点击明确的下一集。若片库很小、你已熟悉每部作品，或简介缺失严重，增加云端判断只会带来等待和维护。先补标签筛选、排序、资料完整性和一键恢复进度，可能比接 AI 更有效。

三个判断变量：

1. 真实痛点是否是“选不出想看的”，而不是“找不到文件/播放不了/资料抓错”。
2. 候选是否有足够简介、标签及可靠约束字段。
3. 加上材料准备、等待和查证后，是否仍比现有筛选更快。

当前判断：**可行性中高，必要性取决于实际选片频率；适合有界试验，尚无证据支持默认上线。** 不通过当前实际片库抽样，不能再提高这个结论强度。

## 4. 推荐的首个功能：“按心情选几部”

首轮固定几类偏好，例如轻松日常、温暖群像、悬疑推理、热血成长；可输入一句补充，但不从第一天支持任意复杂对话。入口建议放在影视/动漫库现有筛选附近，显式点击后运行，沿用现有卡片，不新增聊天页或 QA Dashboard。

首批优先使用已刮削、简介完整的影视候选。代码可在 `src/lib/db-helpers/cinema.ts` 附近新增只读候选投影，供 `/cinema-library` 或 `/cinema` 的明确范围使用；不直接把两类库无差别混合。第一版先做独立实验，不修改现有列表 DTO 或数据库；有收益后再选一个页面接入。季度番库的简介覆盖较不确定，留作后续适配。

执行顺序：

```text
本地筛选：分区、类型、可播状态、已看/未看等
  → 从简介/标签/原排序取得候选
  → 准备公开元数据的最小请求
  → Jev 判断每个候选是否符合指定偏好
  → 本地校验结果 ID、候选版本、状态与资格
  → 优先展示 3 部，保留“查看全部”和原排序
```

“只看本地可播”“排除已看”等私有条件在本地执行，无需发送对应历史字段。即使只发送公开简介，候选集合也可能间接反映收藏兴趣；产品启用时应明确告知这个外发范围。

首轮每次限定 8 个候选。不能简单截取最高评分的 8 部，否则可能根本没召回偏好匹配项。先用标签、简介关键词和媒体类型拓宽候选；命中不足时展示无合适结果或让用户放宽条件，不隐式分页扫描全库。用少量人工认定的匹配片检查候选召回，再评价 Jev 排序，区分“没搜到”和“排错了”。

返回用“符合偏好 / 可能符合 / 不符合 / 资料不足”分组，同组沿用用户选择的本地排序。首轮不展示“你有 93% 会喜欢”；概率不是个人喜欢程度。需要细粒度连续排序时，再评估同标准 Noul 或 Score；不能拿不同单选集合的概率直接比较。

说明文字使用来源可核对的标签与简介短句；固定模板如“标签含日常；简介主要描述人物共同生活”。不可把 Jev 没返回的自由文本推理编成“AI 推荐理由”，也不展示容易剧透的长剧情。

## 5. 实验能力如何复用，产品如何直连 Jev

`H:\jev-lab` 已有共用 Node 核心、`run-local.ps1`、固定 check、dry-run、请求哈希与 Windows Credential Manager 路径。它适合继续承担 check 设计、固定样本和验收，不代表 Bandi 正式运行时必须“连接 Jev Lab”。

产品现已改为 Bandi 主进程直接请求 TypeSafe Jev。此前通过 `H:\jev-lab` 启动器完成的个人版链路保留为历史验收证据；现行直连继续使用同一 `media.fit.v1` 合同、固定模型、字段白名单、结果校验与不自动重试边界，但不把本机绝对路径打进发行版。Jev Lab 退回 check 设计、固定样本与回归工具。

本轮源码核对到的限制：

- `jev-check.mjs` 当前只接受 **Choice / Noul**，不接受 Score；最多 24 个问题、每个 Choice 最多 12 个选项、本地请求最多 64 KiB。
- 官方 API 有 Score，但官方能力不等于本地包装器已经支持。首试采用已有 Choice 类型即可，不为细分分数先扩核心。
- 本地现有 checks 面向 diff、技能、动作选择和 guardrail；本轮列出的目录中没有媒体筛选 check。不能把网页动作或 diff check 填入片单后当作推荐器。

建议新增一个独立的 `media-fit.v1` check，固定 8 个候选槽位、每项一个同义的四选一问题。每个问题完整指向对应候选与用户偏好；空槽位必须返回资料不足或在本地跳过展示。额外排除偏好另问独立问题，不混进可互相抵消的平均分。24 题是本地上限，不是每次必须用满。

输入只含随机候选 ID、公开标题、简短简介、题材及本次偏好。来源 URL、文件路径、库内 ID 映射和元数据指纹保留在本地旁表；观看进度、评分笔记、下载记录和个人账号不发送。

### 实验与产品运行分开

第一步仍在现有 Jev 实验环境准备公开/合成候选，通过共用启动器验证。新增 check 的 questions 和允许字段属于常驻授权之外的变更，**未来首次外发前需要用户确认该具体 check 与 payload**；本轮只写方案，不创建/提交请求。

个人 Windows 版先用薄适配完成了 dry-run、同哈希 live 与界面回读验证，随后已迁移到正式直连：Next 服务端重新生成受限候选并签署 60 秒短时请求，Electron 主进程验签、防重放、复核固定合同后才解密 Key 并请求 TypeSafe。页面拿不到 Key，用户与 Agent 当前的常驻授权也不自动等于应用后台可以永久外发。

产品服务端适配应另有明确的“仅点选时调用”授权及字段展示。服务端只接受受限偏好/候选参数，不接受任意 shell、check 文件路径、端点或模型；不把字符串拼成执行命令。异步响应需绑定查询 ID 与元数据版本，过期结果不覆盖新条件，展示前重新核对可播状态。API 慢或失败时保留原片库，不阻塞播放与导航。

**个人本机过渡适配不能原样打进公开发行版：**别的电脑没有 `H:\jev-lab`，macOS/NAS 也不能照搬 Windows 凭据调用。分发版应由 Bandi 直接调用官方 API，并按平台提供安全凭据方案；Jev Lab 只作为测试真值来源，不成为用户需要安装或配置的组件。

## 6. NAS 媒体中心的三种整合层级

| 层级 | 怎么用 | 当前建议 |
|---|---|---|
| **NAS 存文件，Bandi 运行在 Windows** | 沿用本地/UNC 目录扫描和播放；只把元数据候选交 Jev | **优先**。无需先改成服务器产品；可用性仍需真实共享目录和文件测试 |
| **接已有媒体服务的目录** | 如果未来使用 Jellyfin/Emby/Plex 等，以其目录作为候选来源，在现有界面做语义排序 | 后续选定一个服务再核对 API、权限和播放链接；本轮未验证连接器，不默认三个一起接 |
| **Bandi 本身部署到 NAS** | 处理 Linux/容器、目录映射、持久化、凭据、会话和平台相关依赖 | 暂缓。当前发布合同未覆盖，Jev 只是其中一个可选调用，不是迁移理由 |

不存在“Jev 装到 NAS 后自动看懂所有影片”的步骤。Jev 当前接收文本化信息；视频识别、字幕提取、转码与元数据采集是独立工作。[官方模型边界](https://docs.typesafe.ai/models)

## 7. 分阶段验证与投入控制

### A. 不改产品，先确认语义匹配有收益

建议用 20–30 部公开且有来源的作品元数据，固定 10 条真实风格的选片需求。包含正向偏好、否定偏好、资料缺失、同名续作、无匹配及混合题材。不要发送本机完整片库。

对照三组：原标签/关键词筛选、同样材料下现有主模型、Jev。硬筛选与候选集合相同；先记录候选是否包含可接受作品，再比较结果。Ludi 在看模型标签前标注各需求的可接受/不接受/未知；若是主观偏好无法预标，使用匿名混排后的偏好选择，不把模型自评当真值。

观察四件事：前三项可接受作品的原始数量、找到想看片的时间、资料不足是否诚实保留、硬条件是否被违反。记录端到端 p50/p95 与失败次数，但小样本只作继续/停止信号，不宣称稳定准确率或通用提速倍数。

建议第一轮仅投入半天验证，不含界面开发；最多针对一个集中失败原因调整一次。若候选/简介不足就停止模型调参，转为明确的数据缺口；若普通筛选效果相同或复核更费时，就不接产品。

### B. 个人 Windows 版显式入口

仅在 A 有收益后，做一个入口、一条服务端适配与结果状态。保留原筛选、手动打开和播放。验证点击后可取消等待、切换条件不串结果、失败回退、没有合适结果、资料缺失、候选离线或过期。不自动收藏、下载、移动或更新元数据。

初期不新增数据库表。需要复用判断时，可在既有运行缓存目录存可丢弃结果，键包含公开元数据哈希、check 版本、模型和偏好；候选变化应失效。偏好日志和实际片单属于个人数据，不进公开仓库。是否持久保存另按产品约定决定，本轮不创建缓存或迁移。

### C. 主题标签与更广泛使用

确认频繁使用后，再考虑对公开元数据预计算少量语义标签，让后续筛选主要在本地完成。标签必须有模型/规则版本与来源，不覆盖原 tags，不把“未知”存成否定。换权重、切排序不应重复推理；换资料或问题定义才重算。扩大到家庭共享、第三方媒体目录或 NAS 服务端分别立项。

## 8. 成本、风险和不做的事

官方当前输入价为每百万 token 0.042 美元、输出免费。假设一次总输入 5,000 token，约 0.00021 美元，1,000 次约 0.21 美元；这是量级示例，不是本项目实测，更不是账户额度保证。提示问题与候选都会消耗输入预算，真实成本用返回 usage 计算。[模型说明](https://docs.typesafe.ai/models)

目前更大的成本是补齐资料、误推荐和产品维护。官方也说明中文效果须独立验证，数学/时间比较留给代码，过多无关上下文会影响判断，输入中的对抗性文字可能影响答案。因此简介和评论始终按数据处理，输出 ID 必须属于当前候选集合。[已知限制](https://docs.typesafe.ai/model-jaggedness/jev-1.13)

不做视频全量上传、不发送媒体路径与观看历史、不让“治愈/适合全家”成为保证、不用模型分数替代年龄限制，不让它批准文件删除或触发下载。基础浏览与本地播放继续能在 Jev 不可用时运行。

## 9. 下一步建议

**先批准一个只用公开元数据的媒体筛选实验，而不是直接批准“NAS 全面整合”。** 具体产物是一个媒体 check、固定候选与需求集、一份对照结果。代码复用现有 Jev 核心；通过后再决定个人版 UI 接入。

如果你的实际诉求主要是“按评分、年份、是否完结找片”，直接完善现有筛选即可；如果主要是“我知道想要的感觉，但想不到片名”，Jev 才值得进入第一轮。
