# 外部评分、每周榜单与 Jev 选片信号方案

日期：2026-09-21。状态：方案已确认；现有接入审计、动漫详情 Bangumi / AniList 口碑卡与 Windows 版 Jev 直连代码已完成。IMDb、MAL、Anime Corner 与单集评分尚未实施。

## 结论

1. “按心情选片”不应只看本地文件。候选范围应拆成“本地可播 / 我的追番 / 番剧库与影视库 / 全部资源”，播放能力继续单独标注。
2. 外部评分对“作品口碑、热度、当周讨论度”有价值，但与“轻松温暖、不要复杂主线”不是同一个问题。评分应作为第二条轴，由本地代码筛选和排序；默认不塞进 Jev 的心情判断。
3. 提升 Jev 准确度，优先级是：候选召回覆盖 → 简介与题材完整度 → 可核对的内容描述 → 人工标注与失败分析。原始评分、票数和评论量不是替代品。
4. 详情页可以展示多来源评分与周榜，但必须来源分列、附票数和更新时间。第一期不做一个失真的“综合分”。
5. 单集评分覆盖并不统一：IMDb 数据集可以通过剧集映射与评分表推导；Anime Corner 是番剧的每周投票名次和票数占比；Bangumi、AniList、MAL 当前官方合同没有稳定的单集数值评分字段。

## 双向钢人

### 支持引入多来源信号

- 单一简介很难表达节奏、持续质量、某一集是否口碑爆发或崩坏。周榜和单集评分能补“最近表现”。
- Bangumi、MAL、AniList、IMDb 的人群与评分文化不同，分开展示可以帮助用户看到地区和社区差异。
- 票数、排名变化、连续多周表现能帮助候选召回，避免只从高总分老番里挑片。
- 有来源、可回读的评论共识可以补“节奏慢、主线复杂、感情线占比”等简介经常不写的维度。

### 最强反对意见

- 不同平台的 8.0 不是同一量尺。直接平均会混淆评分体系、样本人数、地区偏好与播出阶段。
- 每周榜是参与投票人群的支持度，不是单集质量的统一评分；热门续作和大社区会天然占优。
- 评论原文带剧透、情绪极端、提示注入、版权与采集许可风险，也会快速放大 token 成本。
- 心情匹配是语义问题。把口碑数字加入同一个 Jev 问题，可能让“高分但沉重”的作品压过真正轻松的候选。
- 数据抓取、跨站身份匹配与缓存维护的成本，很可能高于一次 Jev 判断本身。

### 关键变量

1. 产品首要回答的是“符合我这次心情吗”，还是“整体值得看吗”。
2. 数据是否有稳定、允许使用的接口与可验证身份映射。
3. 是否有 Owner 标签证明新增信号真的提高 Top 3 可接受数量，而非只让结果看起来更权威。

## 提升 Jev 判断准确度的正确分层

```text
候选范围与硬条件（本地代码）
  本地可播 / 我的追番 / 番剧库 / 影视库
  年份、完结、已看、成人分区、是否有资料
        ↓
候选召回（本地规则与检索）
  标题、题材、简介关键词、来源身份、范围平衡
        ↓
心情适配（Jev）
  偏好 + 匿名候选号 + 标题 + 简介 + 标签
  → 符合 / 可能符合 / 不符合 / 资料不足
        ↓
口碑与热度（本地代码）
  Bangumi / AniList / MAL / IMDb / 周榜分别展示
        ↓
最终界面
  “符合这次心情”与“外部口碑”两条轴，不合并成假精确概率
```

### Jev 输入应该增加什么

- 优先补充可靠简介、题材、作品形式，以及来源明确的短内容描述。
- “单元剧 / 连续主线 / 暴力强度 / 恋爱占比 / 节奏”应作为可核对的独立描述；没有证据就保持未知。
- 若用户明确说“高分、热门、近期口碑好”，先由代码用评分/趋势筛出候选，再让 Jev 判断其余语义条件。
- 概率只表示同一次 Choice 的分布集中程度，不解释成“你有 90% 会喜欢”。

### Jev 输入不应该直接增加什么

- 不把五个平台原始分数简单拼在每个候选后面，让模型自行平均。
- 不发送观看进度、下载记录、个人评分笔记或完整收藏史。
- 不批量发送评论原文。若以后验证评论有收益，只发送有来源的短证据摘要，并保留“支持 / 反对 / 资料不足”。

## 多来源评分如何组合

第一期只分开展示，不计算综合分。若后续确有排序需要：

1. 每个来源内部按同季度、同格式做 percentile 或标准化，避免直接比较 8.2 / 81 / 第 3 名。
2. 按投票人数做 Bayesian shrinkage；小样本高分不能压过大样本稳定分。
3. 每周榜使用时间衰减，表达“近期势头”，不替代长期评分。
4. 地区与社区保持独立标签，不把 Anime Corner 的参与者分布外推为全球用户。
5. 综合权重必须可解释、可回放，并用实际选片结果调参，不由 Jev 自行决定。

## 详情页展示建议

### 动漫详情

- “社区口碑”卡：Bangumi、AniList，后续补 MAL；每项显示分数、票数/热度、更新时间和外链。
- “本季走势”卡：Anime Corner 周榜名次、票数占比、上周变化；明确标为社区投票。
- 剧集列表：IMDb 有可靠单集映射时显示 IMDb 单集评分和票数；没有则不占位。Bangumi 的回复数可显示为“讨论”，不能标成评分。

### 影视详情

- 延续豆瓣 / TMDB，补 IMDb 标题分和票数。
- 电视剧可在集列表补 IMDb 单集评分；电影没有单集维度。

视觉上不使用一个大号“综合评分”。来源卡以相同层级并列，用户能看出每个数字来自哪里。

## Jev 的产品连接方式

**Bandi 可以而且正式产品应当直接调用 TypeSafe Jev。** `H:\jev-lab` 不是必需的网络中转服务；它目前被复用，是因为它已经提供固定 check、字段白名单、dry-run、同哈希提交、Windows Credential Manager 取钥、响应校验和运行记录，适合在实验与验收阶段保护外发边界。

把 `H:\jev-lab` 作为发行版运行依赖并不合适：它是本机绝对路径，其他 Windows 电脑、macOS 和 NAS 都不存在。目标架构应为：

```text
界面点击“开始判断”
  → Bandi 服务端重新生成受限候选
  → Bandi 服务端直接请求 TypeSafe /v1/systemone
  → 本地校验候选 ID 与返回结构
  → 页面显示四档结果

Jev Lab：只保留为 check 设计、固定样本和回归验收工具
```

用户已选择由 Bandi 安全保存 Key。现行实现使用 Electron `safeStorage` 调用 Windows 系统加密，配置文件只保存密文；设置页不回显 Key，保存时也不请求 TypeSafe。实际判断由 Electron 主进程使用原生 `fetch` 直连固定 `/v1/systemone` 端点，不新增 SDK 依赖，保持 10 秒超时、单次请求和不自动重试。Next 服务端会重新生成候选，并用仅本次启动有效的密钥签署 60 秒短时请求；主进程验签、防重放并复核字段后才解密 Key。Key 不进入前端 bundle、日志、仓库或 Jev state。

## 数据与维护边界

- 第一阶段使用按需读取 + 可丢弃缓存，不改数据库 schema。
- IMDb 全量 TSV 体积与每日更新适合独立增量索引，不应在详情页请求时临时下载。
- MAL 需要官方 API 客户端身份；本项目当前没有 `malId` 字段，可先通过 AniList `idMal` 做只读映射验证，不立刻迁移 schema。
- Anime Corner 在没有稳定公开 API 与使用许可结论前，只做外链/实验性适配，不成为阻塞详情页的依赖。
- 任一来源失败时保留其他来源与本地页面，不能阻塞播放、追番或 Jev 选片。

## 分阶段顺序

1. **候选范围扩展**：本地可播、我的追番、番剧库/影视库、全部资源。2026-09-21 预览入口已完成；非本地范围尚未授权真实外发。
2. **标题级口碑卡（已完成）**：仓库已有的 Bangumi + AniList 数据已接到动漫详情；影视沿用现成的豆瓣 + TMDB，没有重复建设。
3. **Jev 真实本地候选调用（代码已完成，待桌面实机验收）**：Bandi 主进程已改为直连 TypeSafe，Key 由 Windows 系统加密保存；已授权字段、显式点击和四档结果不变。Jev Lab 仅保留为实验与回归工具。
4. **IMDb 小型索引试验**：验证 20–30 部剧的标题与单集映射、体积和命中率。
5. **周榜试验**：Anime Corner 只作为近期热度轴，先不参与 Jev。
6. **评论证据实验**：只有前述结构化信号仍无法判断节奏/内容时，才测试少量来源明确的摘要。

## 已确认与剩余工作

- 已确认：心情匹配与外部口碑是两条轴；第一期复用现有 Bangumi、AniList、豆瓣和 TMDB 能力，不做综合评分。
- 已确认：Bandi 使用 Electron `safeStorage` 安全保存 Key，由主进程直连 TypeSafe，不读取或依赖 Jev Lab 路径。
- 剩余：用户在重建后的桌面版设置页录入一次 Key，再用真实本地候选完成一次实机点击验收；这一步才会产生新的真实 TypeSafe 请求。
